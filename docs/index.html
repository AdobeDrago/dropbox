Dropbox · Marketing Site Migration

Dropbox on Edge Delivery Services

Rebuilding the dropbox.com marketing site on Adobe Edge Delivery Services. So far that means importing 2 representative pages (the homepage and Dropbox Enterprise) across 2 page templates into Document Authoring, building 12 custom block variants, applying the Dropbox brand design system and rebuilding the production header with its dropdowns and language picker. This is the handoff playbook: what we gathered, what was built, the decisions and assumptions behind it, and what's left to finish.

Project overview

This effort recreates Dropbox's public marketing site on Adobe Edge Delivery Services (EDS), authored through Document Authoring (DA). The source is a React site built on Dropbox's own design system (dwg-* "plank" components). The target follows the EDS block-based model: every production component maps to an authorable block variant, and each page type has a repeatable import script.

Goals

  • Recreate the Dropbox marketing experience on Edge Delivery Services, authored in DA.
  • Identify the site’s page templates and import a representative page for each.
  • Model every production component (split hero, logo marquee, card grids, accordions, video, quote slider) as an authorable block, reusing variants across pages wherever the content model matches.
  • Match Dropbox’s brand identity: Dropbox blue, graphite and coconut surfaces, Sharp Grotesk / Atlas Grotesk type, header and dropdowns.

Approach

  • EDS block-based development only, with one block variant per production pattern (hero-split, cards-integration, …) and author-selectable options where only layout differs (cards-integration (four-up)).
  • Pages grouped into templates; each template gets a page-templates mapping, block parsers and an import script.
  • Design values read from the live site with getComputedStyle, then verified with side-by-side screenshots and per-section height comparisons.
  • Work was built on the dropbox-homepage branch and merged to main (PRs #1 and #2), previewed at main--dropbox--adobedrago.aem.page.

Header & dropdowns Desktop complete

The boilerplate nav was replaced with Dropbox's production header. It's authored as the nav document in DA and decorated by blocks/header/, so authors change menus without touching code. All copy and images live in the nav document; header.js only reads it and adds the interactive chrome.

  • Bar: 72px, solid white, fixed while scrolling. Logo, Products / Solutions / Business / Pricing on the left; language globe, Contact sales, Get app, Sign up, Log in and the blue "Get started" button on the right.
  • Dropdowns: open on hover and toggle on click. Products is a 3×3 grid of icon cards with descriptions; Solutions has three labelled columns (Teams, Use cases, Industries); Get app is a two-link list. A full-width white sheet grows under the bar and the page dims to 50% graphite, as on production.
  • Language picker: the globe opens a modal with all 23 languages in three columns.
  • Geometry: trigger and panel positions match production within a few pixels (Products panel at 189 × 72, 720 × 308).
  • Mobile: below 1200px a hamburger opens a stacked menu with accordion dropdowns. This is a placeholder until the mobile phase runs.
The header loads the nav with a metadata-independent dual fetch (/content/nav.plain.html locally, then /nav.plain.html on DA/EDS), so it renders on every page. It also normalizes production markup, which wraps simple nav links in paragraphs and delivers images as <picture> elements.

Validation

Desktop was validated with independent live comparisons against dropbox.com: panel content (3/3), computed CSS (10/10 elements), link content, panel layout, full visible text (50 phrases) and panel screenshots. The screenshot check caught a real bug: the full-width sheet was painting over the dropdown links once the bar became sticky. It was fixed by raising the nav's stacking order.

Footer Planned

The footer has not been migrated yet. The footer document in DA still holds the boilerplate content, and blocks/footer/ is unchanged from the template.

Dropbox’s footer has six link columns (Dropbox, Products, Features, Support, Resources, Company), social links, and the legal / cookie-preference links. Migrate the copy verbatim, and keep the "Cookies & CCPA preferences" link wired to a working consent mechanism.

  • Typefaces: Sharp Grotesk (headings), Sharp Grotesk 23 (section display headings) and Atlas Grotesk (body). They are licensed Dropbox fonts with no public CDN, so the stacks name them first and fall back to the system sans-serif.
  • Type scale: 16px body. h1 32 → 40px; section display headings 24 → 32px; feature headings 26px / 500. Section intros sit in an 827px centred column.
  • Sections: authors set Style: light-beige, dark or dark-panel (rounded graphite gradient) in Section Metadata. The import transformer does this automatically from the template.
  • Rhythm: 72px above each section, 72px between a section intro and its block, and a 72px band in the upper colour where the background changes into a section that opens with an intro.
  • Buttons: bold link → blue filled primary; italic link → outline secondary; 16px radius, 14px × 24px padding.

Cleanup rules

  • Removed before parsing: consent iframe, One Tap container, modal portals, skip link, A/B-test sticky CTA bar and empty experiment mounts.
  • Removed after parsing: global nav and footer, tracking iframes, scripts, the marquee pause control, and transparent .mov UI animations that have no poster.
  • Default-content CTAs are marked by style: primary → bold (filled button), outline → italic (outline button).
Images. Imported pages reference Dropbox’s image CDN (fjord.dropboxstatic.com). The EDS preview pipeline rejects SVGs over ~40KB, so for Enterprise nine large SVGs (security illustrations and app logos) were rasterized to PNG and, with one rate-limited photo, hosted in DA under images/enterprise/. The local import still points at the originals.

Page-level fixes from the comparison

  • Intro gap: 72px between a section’s heading / intro and the block that follows (card grids had only 4–16px).
  • Colour bands: at a background change, the section above keeps a 72px band in its own colour, because production planks carry a 72px margin painted in the upper colour.
  • Heading column: section headings and intro text sit in production’s 827px column instead of running full width.
  • No horizontal scroll: main uses overflow-x: clip so full-bleed media can never cause sideways scrolling.

Decisions & assumptions Handoff

The choices behind the build. Read these before extending the work.

DecisionRationale / assumption
Reuse before new variantsEnterprise reused hero-split and cards-integration rather than creating near-duplicates. Layout-only differences became an author option (four-up); shared parsers were checked to produce byte-identical homepage output.
Design values from computed stylesColours, sizes and spacing were measured on the live site. Block passes kept the homepage pixel-identical when shared blocks changed.
Section styles via Section MetadataBackgrounds are section styles (light-beige, dark, dark-panel), not baked into blocks. Production applies Section Metadata server-side; a small client-side fallback in scripts.js covers the local preview and does nothing when the server has already applied it.
System font fallbackSharp Grotesk and Atlas Grotesk are licensed and not available on Adobe Fonts or Google Fonts. The stacks name them first, so self-hosting the licensed files later needs no CSS changes.
Content-first headerAll nav copy, links and icons live in the DA nav document; the header code reads it generically (no site-specific functions), so menus are edited by authors.
Desktop nav from 1200pxProduction hides its triggers below roughly 1280px. The project’s allowed breakpoints are 600 / 900 / 1200, so 1200 was used. A few blocks use production’s own 480 / 1024 breakpoints where layouts depend on them.
Language picker as UI onlyDropbox switches locale with a script, and the URL parameter has no effect. The modal and all 23 languages are migrated, but selecting one only closes it until localized pages exist.

Known limitations & accepted quirks Review

Accepted for this delivery. Each one is a candidate for follow-up before production.

  • Mobile header not built
    Below 1200px the header uses a basic placeholder hamburger menu. The mobile phase (analysis, slide/accordion behaviour, width checks) is waiting on desktop sign-off.
  • Footer is still the boilerplate
    See Footer.
  • Content not yet published
    Pages, nav and footer are previewed but not published to the live site. Publish from DA (or the Sidekick) once reviewed.
  • Fallback fonts
    Headings wrap differently and weight-500 text renders lighter than production until the licensed fonts are self-hosted.
  • Testimonial CTAs are plain text
    "Watch testimonial" / "Watch webinar" open a modal video on production and have no URL. Authors need to add video links to make them clickable.
  • Media trade-offs
    Homepage UI animations (transparent .mov) were dropped; the security panel shows only its main product image. App-integration cards on Enterprise are two 4-card blocks rather than one 8-card block.
  • Images on Dropbox’s CDN
    Most images still load from fjord.dropboxstatic.com, which rate-limits heavy traffic. Consider moving all media into DA before go-live.

Developer notes

Run it locally

# local code, previewed content npx -y @adobe/aem-cli up # → http://localhost:3000/ (imported pages are served under /content/ in this workspace) # inspect the markup a block receives curl -s http://localhost:3000/content/enterprise.plain.html

Block CSS conventions

Keep block CSS scoped to .blockname; treat -wrapper / -container as section classes. Where a block needs spacing that depends on what precedes it (e.g. the 72px intro gap), use .default-content-wrapper + .x-wrapper > .x so the styled element is still the block. Authors can omit or add cells, so decorators target content by shape (picture, heading, link) rather than fixed positions.

Shared blocks

hero-split and cards-integration are used by both templates. Before changing either, capture the homepage before and after: the Enterprise work kept it byte-identical.

Re-running an import

Add URLs to the matching tools/importer/urls-*.txt (or the template in page-templates.json), bundle the template's import-*.js and run the bulk importer. Generated *.bundle.js files and reports are not committed.

Before uploading imported pages to DA, check for SVGs over ~40KB and for images the CDN rate-limited (the preview step fails with AEM_BACKEND_FETCH_FAILED / "failed validation"). Rasterize or rehost those images in DA.
